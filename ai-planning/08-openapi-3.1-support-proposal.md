# 08 — Proposal: supporting OpenAPI 3.1 (and 3.2) alongside 3.0

## Context

This library is hard-scoped to OpenAPI 3.0 today — the README says so explicitly,
the root namespace is just called `Swagger`, and every behavioral module
(`lookup.ts`, `type-checks.ts`, `operation-grouping.ts`) is written directly
against the 3.0-shaped types in `swagger.ts`. OpenAPI 3.1 has been out since
2021 and is what a growing share of newer specs are written against (it's the
version [PR #33](https://github.com/robertmassaioli/atlassian-openapi/pull/33),
still open, was trying to partially support by adding `"null"` to `SchemaType`
— which is exactly the kind of half-step this proposal is meant to replace
with a real plan). OpenAPI 3.2 also shipped in September 2025 as a
"zero-breaking migration from 3.1," which matters a lot for scoping: it means
**getting to 3.1 support is the real project here — 3.2 is a small follow-on**,
not a second equally-sized effort.

This document covers what it would actually take: the concrete spec
differences, what in this codebase assumes 3.0 and why, the design decisions
that are genuinely open (not just mechanical), a phased plan, and an effort
estimate.

## What's OpenAPI-3.0-specific in this codebase today

| File | Coupling to 3.0 |
|---|---|
| `src/swagger.ts` (895 lines) | The entire `Swagger` namespace — every interface (`Schema`, `Parameter*`, `SecurityScheme`, etc.) is 3.0-shaped. Header comment claims it's generated by `json-schema-to-typescript` from `swagger-v3.json` and "DO NOT MODIFY IT BY HAND" — but the Atlassian extensions (`x-atlassian-oauth2-scopes`, `x-atlassian-data-security-policy`, `x-atlassian-auth-types`, `x-bearer-type`, `x-atlassian-narrative`, etc.) **do not appear anywhere in `swagger-v3.json`** (verified — zero matches for `x-atlassian`), meaning this file has already drifted from its stated source of truth and is being hand-maintained in practice. |
| `src/type-checks.ts` (409 lines) | `SwaggerTypeChecks` — every predicate (`isSchema`, `isReference`, `isSecurityScheme`, …) does structural/duck-typing against 3.0's exact key sets (`schemaStandardKeys`, `headerWithSchemaKeys`, etc.), and `isReference` assumes "has `$ref`" and "is a real value" are mutually exclusive — true in 3.0, **not true in 3.1** (see below). |
| `src/lookup.ts` (152 lines) | `SwaggerLookup.InternalLookup`'s `performLookup` is genuinely version-agnostic JSON-pointer traversal, but every public method is typed directly against `S.Schema`, `S.Reference`, etc. from the 3.0 namespace. |
| `src/operation-grouping.ts` (264 lines) | Reads `PathItem`/`Operation`/`Tag` fields (`.tags`, `.summary`, `.get`/`.put`/…) that are **unchanged between 3.0 and 3.1** — this module barely touches `Schema` at all, which matters for scoping below. |
| `package.json` | `"files"` lists `"swagger.v3.json"` (dot-separated) but the actual file in the repo is `swagger-v3.json` (dash-separated) — this mismatch means the JSON Schema source almost certainly isn't shipped in the published package today. Worth fixing regardless of this proposal, but especially relevant if a second schema source is about to be added. |

## What actually changes in the spec

### 3.0 → 3.1: the real jump

The headline change is that OpenAPI 3.1's Schema Object becomes a **full JSON
Schema 2020-12 document** instead of the OpenAPI-specific subset of JSON
Schema Draft 5 that 3.0 used. Concretely, for the `Schema` interface at
`swagger.ts:357-395`:

- **`nullable: boolean` is gone.** Nullability is expressed by putting
  `"null"` in `type`, which is now allowed to be an array:
  `type?: SchemaType | SchemaType[]` where `SchemaType` gains `"null"`. This
  is the exact thing PR #33 was trying to do, but only half of it —
  `nullable` also needs to go, and `type` needs to become an array, not just
  gain one more string literal.
- **`exclusiveMinimum`/`exclusiveMaximum` change from booleans to numbers.**
  3.0: `{ minimum: 7, exclusiveMinimum: true }`. 3.1: `{ exclusiveMinimum: 7 }`
  directly, with `minimum` dropped. This is a breaking shape change on an
  existing field name, not an addition.
- **`example` (singular) is joined by `examples` (array)** at the Schema
  level, matching plain JSON Schema. (Note: this is distinct from the
  `example`/`examples` already on `Parameter`/`MediaType`/`Header` in 3.0,
  which don't change.)
- **`$ref` can have sibling keywords.** In 3.0, an object with `$ref` is
  *only* `{ $ref: string }` — nothing else is meaningful alongside it. In
  3.1, `$ref` follows JSON Schema semantics, so `{ $ref: '#/...', description:
  'override' }` is valid and the sibling keywords apply as annotations. This
  is the change with the most real design impact — see below.
- **A large batch of JSON Schema 2020-12 keywords become legal**:
  `prefixItems`, `patternProperties`, `if`/`then`/`else`, `const`,
  `contains`/`minContains`/`maxContains`, `unevaluatedProperties`,
  `dependentRequired`/`dependentSchemas`, `$id`/`$anchor`/`$defs`, and a
  Schema can now just be the boolean `true` or `false`.
- **New top-level fields on the document itself**: `webhooks` (shaped exactly
  like `paths`, describing calls the API makes *to* the caller),
  `jsonSchemaDialect` (declares the default `$schema` for all Schemas),
  `components.pathItems` (a new reusable, `$ref`-able Path Item bucket).
- **`License.identifier`** — an SPDX expression, alternative to the existing
  `url` field.
- **`openapi` version string** moves from `^3\.0\.\d(-.+)?$` (see
  `swagger-v3.json:8`) to `3.1.x`.
- Smaller items surfaced during implementation are likely (e.g. `mutualTLS`
  was added as a `SecurityScheme` variant around this era) — Phase 1 below
  includes producing an exhaustive diff against the official schema rather
  than relying on this list alone.

### 3.1 → 3.2: comparatively small

3.2 (released 2025-09-19) is explicitly a **zero-breaking migration from
3.1** — every valid 3.1 document is still valid 3.2. It adds
`additionalOperations` (describing non-standard HTTP verbs on a `PathItem`),
hierarchical tags, first-class streaming markers, and richer examples,
without touching the Schema Object model further. The practical
consequence: once this library supports 3.1 properly, 3.2 support is a small
incremental PR on top, not a second version of this whole proposal.

Sources: [Upgrading from OpenAPI 3.0 to 3.1](https://learn.openapis.org/upgrading/v3.0-to-v3.1.html), [OpenAPI 3.2.0 release notes](https://www.speakeasy.com/openapi/release-notes/), [OpenAPI 3.2.0: Evolving with Modern API Patterns](https://medium.com/@okoanton/openapi-3-2-0-evolving-with-modern-api-patterns-9977972e9381).

## The design questions this raises for this specific codebase

1. **Backward compatibility is non-negotiable.** `Swagger.SwaggerV3` and
   everything under it is public API consumed by other Atlassian tooling.
   None of it can be renamed or reshaped. Whatever 3.1 support looks like,
   it has to be **purely additive** — new exports, zero changes to existing
   ones — so this ships as a semver-minor release, not a major.
2. **`isReference`'s assumption breaks structurally, not just by type.**
   `type-checks.ts:94-96` today: `typeof s === 'object' && s !== null &&
   '$ref' in s` — and every caller (especially `lookup.ts`'s
   `performLookup`) treats "has `$ref`" as "is *nothing but* a reference, go
   look it up and use the result instead." Under 3.1, an object can
   legitimately be `{ $ref: '...', description: 'override' }`, and the
   *correct* behavior is to resolve the reference **and** apply the sibling
   keywords as annotations on top. This is a real semantic decision, not a
   type-widening exercise: does `InternalLookup` merge sibling keywords into
   the resolved value, ignore them, or is that left to the caller? This
   needs an explicit answer before writing the 3.1 version of `lookup.ts`.
3. **Duplicate the behavior modules per version, or generalize them?** The
   three behavioral files aren't equally coupled to Schema internals:
   - `operation-grouping.ts` barely touches `Schema` — it works with
     `PathItem`/`Operation`/`Tag`, which are essentially unchanged in 3.1.
     This is the best candidate to **generalize** (a type parameter for
     which Operation/PathItem shape it's working with) rather than fork.
   - `lookup.ts`'s `performLookup` is pure JSON-pointer mechanics with a
     type-guard callback — also a good generalization candidate, *once* the
     `$ref`-siblings question above is answered, since that answer changes
     what "resolve" actually does.
   - `type-checks.ts` is the one file that's fundamentally about "what does
     this exact key set mean," and 3.0 vs. 3.1 key sets genuinely differ
     (`nullable` valid vs. not, `examples` vs. `example`, boolean schemas,
     etc.). This is the strongest candidate to **fork** into a parallel
     `SwaggerTypeChecksV31`, since trying to parameterize duck-typing logic
     over two different key sets would be more convoluted than just having
     two clear, separately-testable implementations.
4. **How much of Schema should be hand-modeled vs. borrowed?** 3.1's Schema
   Object is, by design, *just* JSON Schema 2020-12. Hand-maintaining every
   keyword via `json-schema-to-typescript` (like `swagger.ts` does today) is
   one option; depending on an existing JSON Schema 2020-12 TypeScript
   definition for the `Schema` type specifically is another, and would
   reduce the ongoing burden of tracking JSON Schema keyword additions
   ourselves. Worth a build-vs-depend decision in Phase 1, not before.
5. **Fix the generation-pipeline drift first, or it gets solved twice.**
   `swagger.ts` no longer matches its stated source (`swagger-v3.json`)
   because Atlassian extensions were hand-added post-generation with no
   documented process for redoing that after a regeneration. Adding a
   second spec version to maintain without fixing this first means solving
   the same "how do hand-added extensions survive regeneration" problem
   twice, independently, for two files.

## Recommended approach — phased

### Phase 0 — Fix the generation pipeline (prerequisite, ~0.5–1 day)

Split each spec version's types into a **generated base** (straight output of
`json-schema-to-typescript` against the official OAI schema, genuinely never
hand-edited) and a **maintained Atlassian-extensions layer** (a small,
version-agnostic-where-possible file of interfaces for `x-atlassian-*` and
friends, combined with the base via intersection types or module
augmentation). This makes `swagger.ts` regeneratable again, gives the new
3.1 types the same treatment from day one, and lets the two versions share
the Atlassian-extension definitions where their content is identical (most
of them are — `x-atlassian-oauth2-scopes`, `x-atlassian-auth-types`, etc.
aren't OpenAPI-version-specific concepts). Also fix the `swagger.v3.json` /
`swagger-v3.json` filename mismatch in `package.json`'s `files` while touching
this area.

### Phase 1 — 3.1 types (~1–2 days)

- Source the official OpenAPI 3.1 JSON Schema from the OAI's own repository,
  producing an exhaustive diff against `swagger-v3.json` rather than relying
  solely on the summary above.
  Confirm the `nullable`→`type`-array, `exclusiveMinimum`/`exclusiveMaximum`,
  `example`/`examples`, `webhooks`, `jsonSchemaDialect`, `components.pathItems`,
  and `License.identifier` changes are all accounted for.
- Generate a new `src/swagger-v31.ts` (naming to match the existing
  `SwaggerV3` interface pattern — likely a `SwaggerV31` namespace with a
  `SwaggerV31` root interface), reapply the Atlassian extension layer from
  Phase 0.
- Decide the build-vs-depend question for the Schema type (design question
  #4 above).

### Phase 2 — Behavior modules (~3–5 days, the judgment-heavy part)

- Resolve the `$ref`-with-siblings question (design question #2) — this is
  a real design decision to make explicitly, ideally with Robert's input,
  before writing code that depends on the answer.
- Generalize `lookup.ts`'s `performLookup` machinery with a type parameter,
  reusing it for both `SwaggerLookup` (3.0) and a new 3.1 equivalent, rather
  than forking 150 lines wholesale.
- Fork `type-checks.ts` into `SwaggerTypeChecksV31` with 3.1-correct key
  sets and boolean-schema handling; the 3.0 version stays untouched.
- Generalize `operation-grouping.ts` over the Operation/PathItem shape (a
  type parameter, since the logic itself doesn't change), or confirm via the
  Phase 1 diff that the types are close enough to share directly.

### Phase 3 — Fixtures and tests (~2–3 days)

Mirror the coverage bar already established for the 3.0 modules (per
`ai-planning/07-testing-strategy-proposal.md` and the work that followed it):
real 3.1 example documents as fixtures (including at least one exercising
`$ref` siblings, array `type`, and a boolean schema), a full predicate suite
for `SwaggerTypeChecksV31`, and the same `Lookup` edge cases (external ref,
dangling ref, circular ref) re-verified against the generalized
implementation.

### Phase 4 — Public API and docs (~0.5 day)

- Export the new namespace/functions from `index.ts` alongside the existing
  ones — no changes to existing exports.
- Update the README to describe both supported versions explicitly (it
  currently states 3.0 only, unconditionally).
- Ship as a semver-minor release.

### Later — 3.2 (small follow-on once 3.1 lands)

Given 3.2's "zero-breaking migration from 3.1," this should mostly be:
`additionalOperations` on `PathItem`, hierarchical tags, and whatever
streaming/example refinements are actually useful to Atlassian tooling
consumers — estimated at 2–3 days once the 3.1 groundwork above exists,
versus being a second multi-week effort.

## Open questions for Robert

- **`$ref`-siblings semantics** (design question #2) — this is the one
  decision that most changes what Phase 2 actually builds, and is a genuine
  judgment call about desired behavior, not something to infer from the spec
  alone.
- **Build vs. depend on an existing JSON Schema 2020-12 TypeScript type**
  (design question #4) — affects how much of Phase 1 is generation-pipeline
  work versus adding a dependency.
- **Naming**: `SwaggerV31` (matching the existing `SwaggerV3` convention) vs.
  something that reflects OpenAPI 3.1's own move away from "Swagger"
  branding (e.g. `OpenApiV31`). Worth deciding once, since it's public API.
- Whether this is worth doing at all before or after resolving PR #33 — that
  PR's underlying question (should this library model 3.1-style nullability)
  is effectively the same question this whole proposal answers properly, so
  landing this makes #33 moot rather than needing a decision on it in
  isolation.

## Verification

- Existing 3.0 test suite (144 tests as of `ai-planning/07`) continues to
  pass unmodified — proof the change was additive.
- New 3.1 test suite reaches comparable coverage to the 3.0 modules under
  the thresholds already configured in `jest.config.js`.
- A real-world OpenAPI 3.1 document (e.g. an Atlassian API spec already
  written against 3.1, if one exists, or a well-known public 3.1 example)
  round-trips through `SwaggerLookup`/`SwaggerTypeChecksV31` correctly,
  including at least one `$ref`-with-siblings case.
- `npm run build && npm run lint && npm run test:coverage` all pass with no
  changes required to existing 3.0-consuming code.
